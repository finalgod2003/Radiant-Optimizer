## 3. 实现方式比较

| 方案                                 | 优点                                                                           | 代价                                                  | 判断                               |
| ------------------------------------ | ------------------------------------------------------------------------------ | ----------------------------------------------------- | ---------------------------------- |
| C# / .NET 10 / WPF 客户端 + 现有网站 | 面向 Windows；便于组织 Windows API、进程和系统设置访问；桌面与网页服务边界清楚 | 桌面 UI 使用 XAML，需要单独维护；开发机需补 SDK       | 推荐，产品核心工作在 Windows 本机  |
| Tauri 2 / React / Rust + 现有网站    | 可复用部分 React 展示组件；通过原生后端实现系统操作                            | 增加 Rust 与 Windows 编译工具链，系统适配工作仍然存在 | 可选，适合更强调前端代码复用的团队 |
| Electron / React + Windows 执行器    | UI 与现有前端技术接近                                                          | 需维护渲染进程隔离及原生执行边界，并评估运行时开销    | 可选，首版不优先                   |

此判断是本项目的工程建议，并非对参考产品技术栈的推断。参考：[WPF](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/)、[.NET 支持周期](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)、[Tauri 架构](https://tauri.app/concept/architecture/)、[Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)。

建议网站继续使用 TanStack Start / React / Paraglide / Drizzle；桌面应用采用 .NET 10 WPF，首个打包目标为 Windows x64。Windows 10 和 11 的具体支持版本由兼容测试结果发布，不能由一次本机运行推断全部兼容。

## 4. 完整范围与开发顺序

完整目标保留全部六组功能，分成可单独验收的子项目。第一批交付同时包含真实客户端、网站和授权；它是完整产品的首个可用版本，不表示全部高级功能已经完成。

### 第一批：可使用、可恢复、可激活

客户端：

1. 真实硬件概览：CPU 型号与活动、内存、磁盘容量、显卡型号、操作系统版本；无法读取的传感器明确显示不可用。
2. 只读检测：检查电源计划、磁盘剩余空间、支持的系统设置，给出可解释的发现，不生成没有依据的健康分数。
3. 首批设置：支持的用户级游戏/捕获设置，以及现有电源计划的查看与切换。每项先读取当前值、展示影响、记录原值，再执行和核验。只有通过目标 Windows 版本测试的项目才启用。
4. 恢复中心：按操作查看原值、目标值、时间、结果与重启需求；恢复单项或一次批次，并处理外部更改造成的冲突。
5. 实时进程列表：查看 CPU 与内存活动。首批用于诊断，关闭应用能力在后续独立实现。
6. 基础网络与输入工具：连接延迟、DNS 解析时间、鼠标点击、键盘按键、反应时间、瞄准练习、坏点颜色、手柄输入预览。显示测量方法与设备支持情况。
7. 设备激活、授权状态、断网宽限和下载更新入口。

网站与后台：

1. 产品首页、功能页、Free/Premium 定价、下载页和激活说明。
2. 登录、注册、订单记录、授权列表、绑定设备与解绑入口。
3. 一次性付款确认后发放一台设备的产品授权；退款或管理员撤销后禁止续期。
4. 管理员授权查询、撤销、购买与激活事件记录。
5. 英文默认、支持中文；通过现有主题基础统一产品风格。

首批验收链路：下载并打开应用 → 读取真实本机信息 → 预览一个支持的设置变更 → 应用并读取核验 → 恢复原值；另一路为测试付款 → 服务端确认订单 → 发放授权 → 客户端绑定 → 第二台设备超额激活被拒绝 → 解绑后可重新激活。

### 第二批：游戏、应用与网络工具

- 游戏配置适配器：逐个游戏确认配置格式与安装路径，读取、预览、备份、写入、恢复；配置版本不支持或游戏正在覆盖文件时阻止写入。
- 应用配置、启动行为检查、会话前选定应用的正常关闭，以及调用系统卸载流程。
- CPU 拓扑与选定进程的核心分配；使用进程实例身份避免 PID 复用误操作，支持恢复原亲和性。
- 自有带宽测试端点、下载/上传速度、负载延迟和连接路由；测试可以取消并有流量、时长上限。
- 有系统与网卡支持证据的网络设置，逐项纳入同一备份恢复机制。

第二批完成条件：已公布支持清单里的每个配置适配器都有版本检测与恢复测试；客户端关闭、重新打开后仍能找到备份。测速结果关联实际测试端点，不能把普通 HTTP 往返时间直接称为游戏 ping。

### 第三批：驱动、性能与高级诊断

- NVIDIA 支持的驱动设置：通过正式接口识别能力、读取和修改已验证项目，并保存原值。硬件或驱动不支持时保持禁用。[NVIDIA NVAPI](https://developer.nvidia.com/nvapi/get-started)
- 游戏 FPS、帧时间采集与浮层：评估 PresentMon 的 ETW 数据路径，并验证各渲染模式与游戏兼容性；将采样结果、缺失数据和适用范围明确呈现。[PresentMon](https://github.com/GameTechDev/PresentMon)
- 存储读取测试：限制目标文件、时长与资源量，保存可比较的测试条件和结果。
- 显存测试：独立限定工作量与取消机制，结果仅描述测试样本；在有适配 GPU 的机器上验证后发布。
- 完善手柄、音频、显示与计时工具，以及兼容性说明。

第三批验收针对实际采样与支持范围，不以营销页面里的演示 FPS 数字作为性能承诺。高级工具完成前不在下载页标成已支持。

## 5. 客户端架构

建议新增独立 `desktop/` 工程目录：

- `App`：WPF 窗口、页面、主题、中文/英文资源与交互状态。
- `Core`：检测结果、能力描述、优化项、变更记录和恢复流程等纯业务模型。
- `Windows`：硬件与进程读取、注册表和电源计划适配器、受限的提权执行器。
- `Licensing`：设备授权、签名校验、HTTPS 通信和本地凭据保管。
- `Tests`：能力判定、变更状态机、部分失败、恢复冲突和授权状态测试。

普通检测保持普通用户权限。确需管理员权限的动作由独立执行器接收固定 action ID 与校验后的参数；执行器自行复核能力、参数与调用者。它不接受 UI 提供的任意脚本、任意注册表路径或 shell 命令。

电源计划能力优先使用 Windows 提供的接口；如调用 `powercfg`，使用固定命令和已枚举出的 GUID，核验退出码及执行后的实际值。[Microsoft powercfg 文档](https://learn.microsoft.com/en-us/windows-hardware/design/device-experiences/powercfg-command-line-options)

每个操作依次执行：能力检查 → 原值快照 → 记录待执行状态 → 修改 → 回读核验 → 成功或失败记录。写入前必须已经持久化原值。恢复精确保留原值的类型与“原值不存在”状态。

失败不能统一显示成功。批次中断后提供已应用、未应用和失败的明细；下一次启动可以从记录恢复。发现当前值已被其他程序更改时，展示差异后再由用户选择恢复。

客户端主窗口建议按“概览、检测与设置、游戏、应用、网络、监控、工具、恢复、账号”组织；每一页明确区分可运行、硬件不支持、需要授权和尚未发布的能力。

## 7. 授权与支付设计

### 数据与边界

建议增加 `productLicense`、`deviceActivation`、`desktopAuthGrant`、`licenseEvent` 四类数据。下载版本从部署配置或已发布的版本清单读取，不为尚不存在的安装包生成可下载按钮。

- 一个成功订单最多创建一条对应产品授权，订单关联有数据库唯一约束。
- 首版每个授权最多一台活动设备；槽位占用必须通过唯一约束或条件更新保证，不能依赖先计数再插入。
- 保存设备显示名、随机安装标识、令牌摘要、时间和撤销状态；设备凭据不赋予网页管理员权限。
- 授权状态至少区分 active、refunded、revoked；记录事件用于解释状态变更。

新增 `src/modules/licenses/service.ts`，依赖仅来自 core、config、lib 和 Drizzle。支付与授权由 API 路由编排，遵守模块不互相导入的项目规则；授权模块通过订单表核实归属、产品与服务端付款状态。

### 购买与发放

浏览器提交商品 ID → 服务端取得实际价格 → 支付服务创建订单 → 已验签回调或服务端查询确认支付 → 幂等发放授权 → 账户页可见。

发放失败时保留可重试状态；重复 webhook 或账户侧对账不会重复创建授权。收款金额、币种、商品、支付环境及折扣结果按提供商的权威记录核对。演示的 test amount 设置不能导致生产授权被低价解锁。

退款事件需映射到订单并撤销授权。已撤销授权即使遇到旧的成功 webhook，也不能重新激活。首批商业联调先验证一个支付提供商，其他提供商逐个适配与验收。

### 客户端登录与激活

1. 客户端申请短时设备授权请求，获得用户可见验证码和独立的高熵轮询凭据。
2. 客户端打开系统浏览器访问本项目的设备激活页。用户登录并确认设备、选择自己的授权。
3. 服务端检查授权状态和设备槽位，客户端凭原始轮询凭据换取该设备的受限凭据。
4. 用户验证码有效期为 5 分钟；请求仅能兑换一次，轮询有频率限制。
5. 本地凭据使用 Windows 用户级 DPAPI 保护；服务端保存摘要并支持撤销。[Microsoft ProtectedData](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.protecteddata)
6. 服务端签发包含设备、权限、到期时间和签名密钥 ID 的离线凭证。客户端只包含验签公钥。
7. 建议离线宽限 7 天，联网每天刷新。离线退款/撤销最迟随凭证到期生效；此期限需要在产品界面说明。
8. 解绑后旧设备不能刷新授权；账户页记录该操作。免费检测和恢复既有修改的能力不因付费授权到期而被锁住。

## 8. 发布与验收

- 桌面：可重复执行的 release build，Windows x64 测试包、校验和、版本清单及安装/卸载说明。正式公开分发前完成签名与更新验证。

- 数据库：开发使用 `db:push`；生产生成迁移 SQL 并按项目要求先让用户审阅，再应用。

支付测试通过、未签名本地包可运行、生产可售卖是不同的验收阶段，交付记录分别说明，不能互相替代。

## 9. 已确认的实施决定

建议采用 C# / .NET 10 / WPF 客户端，复用现有网站与 SaaS 后端；按第一批基础与商业链路、第二批游戏应用与网络、第三批驱动与高级监控的顺序完成完整范围。网站首页转为产品入口，游戏目录保留在 `/games`。

确认后先为“授权后台”和“客户端检测/恢复”分别形成可独立验收的实施计划，再按依赖推进客户端与网站联调。
